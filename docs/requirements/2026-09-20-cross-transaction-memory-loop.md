# 一、本轮核心目标

现在借书和还书是两个单独测试。

这一轮将它们连接成：

```text
顾客 A 来借书
↓
玩家检查书
↓
书上本来就有一个旧折角
↓
玩家借出
↓
A 离开

另一名顾客 B 来办理业务
↓
完成

顾客 A 再次回来
↓
归还刚才那一本书
↓
旧折角仍然存在
↓
同时可能出现新的污渍
↓
玩家自己回忆：
“折角原来就有，但污渍以前没有。”
↓
决定是否要求赔偿
```

这个循环才是本游戏真正的核心。

# 二、最重要的设计规则

## 系统知道历史。

## 玩家不知道历史。

后台必须保存：

- 这是什么书
- 它借出前有哪些损坏
- 它借出去后增加了什么损坏
- 谁借走了
- 谁还回来
- 当前真实书况

但是正常游戏界面绝对不能提供：

- 借出时截图
- 借出时书况
- “旧损坏”
- “新增损坏”
- 自动比对
- 损坏日志
- 历史记录按钮
- 红绿提示

玩家只能依靠：

**自己看过以后留下的记忆。**

# 三、建立持久化 Book Instance

不要把每次交易中的书当成全新的临时模型。

建立真实的：

```js
BookInstance
```

例如：

```js
{
  instanceId: "book_lighthouse_001",
  definitionId: "distant_lighthouse",

  title: "远方的灯塔",

  status: "IN_LIBRARY",

  holderCustomerId: null,

  damages: [
    {
      id: "fold_corner_01",
      type: "corner_fold",
      location: "front_cover_bottom_right",
      createdAt: "BEFORE_GAME",
      active: true
    }
  ]
}
```

后续借出：

```js
status = "ON_LOAN"
holderCustomerId = "customer_01"
```

还回来：

```js
status = "IN_RETURN_TRANSACTION"
```

交易完成：

```js
status = "IN_LIBRARY"
holderCustomerId = null
```

# 四、BookDefinition 与 BookInstance 分离

建议明确区分：

## BookDefinition

定义书本身：

```js
{
  id,
  title,
  cover,
  pages,
  category
}
```

## BookInstance

定义这一实体副本现在的状态：

```js
{
  instanceId,
  definitionId,
  damages,
  loanState,
  holderCustomerId
}
```

这样未来：

同一本书名可以有不同实体副本。

也方便继续增加：

- 书籍丢失
- 多次损坏
- 特殊书
- 异常书

# 五、损坏也必须持续存在

损坏不是交易结束后消失。

例如：

### 初始状态

《远方的灯塔》

有：

```text
右下角旧折角
```

A 借走。

后来归还时新增：

```text
第三页咖啡污渍
```

那么下一次再借出去时，这本书应该同时有：

```text
右下角折角
+
第三页咖啡污渍
```

也就是说：

玩家如果以后再次遇见它，

需要记忆的书况会逐渐变复杂。

# 二十一、最终正确性

对于测试案例：

```text
旧折角 → 不追究
新增咖啡污渍 → 要求赔偿
```

然后：

正常收书。

才是完全正确。

如果：

旧折角也罚了：

错误。

如果：

咖啡污渍漏罚：

错误。

如果：

两处都没有检查：

错误。

但是所有错误：

**都延迟到未来工资结算。**
